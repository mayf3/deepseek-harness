# Agent Note: 在不可读祖先处终止附件持久性证明

Status: implemented

[English](2026-10-08-attachment-durability-proof-permission-boundary.md) | 中文

## 问题

`saveImageFile` 以只读方式打开 `DSH_HOME` 的每一级祖先目录并逐级同步、直至文件系统根目录，为每个进程一次性证明 home 的持久性。部署中完全可能出现 home 位于另一账号的仅穿越（traverse-only）目录之下（例如运行时根目录归服务账号所有、mode 为 `0711`，其下的 homes 归非特权运行账号所有）。以运行账号身份打开这个祖先会得到 `EACCES`，该错误在 `saveImageFile` 的包装 `try` 之前逸出，导致这类部署里的每一次图片保存都失败——生产环境中表现为 14 条回执里每次 `imagegen` 工具调用都返回 `EACCES: permission denied, open '<runtime-root>'`，而生成本身已经成功。

## 决策

`ensureDurableDirectory` 的祖先遍历在遇到第一个无法以 `EACCES` 或 `EPERM` 打开的祖先时停止，并把该祖先视为有效持久边界。进程读不了的目录同样也无法增删其目录项，因此位于其上（含其自身）的内容的持久性既不是该进程的义务，也无法由它证明；越过边界的同步从来不是可达语义，只是一次崩溃而已。进程打得开的祖先仍保持到文件系统根的完整证明不变；非权限类的同步失败依旧大声传播。

## 已考虑的备选方案

**放宽部署布局**——把 home 移到服务账号边界之上，或放宽运行时根目录的 mode。拒绝：这会改动共享生产基础设施并重新经历一次部署切换，而存储本身能够承担的代码假设不该靠它来解决。

**跳过打不开的祖先并继续向上遍历。** 拒绝：遍历的目的是给出一个进程能够担保的边界；祖先一旦打不开，证明就已经有界，继续遍历只会耗费系统调用去证明存储并不依赖的任何事情。

**把遍历失败包装成 `ATTACHMENT_WRITE_FAILED`。** 拒绝：把结构性的部署错配伪装成存储错误，会掩盖运维需要的唯一信号；权限错误现在会在发布之前终止遍历，只有真正的发布失败才会到达那个包装器。

## 后果

跨账号 home 布局下的图片与附件保存无需任何改动即可工作；权限边界之下的持久性保证不变，边界之上如实有界。病态的只写祖先（可写不可读、`0---` 风格 mode）会让证明提前终止，尽管该目录进程可变更；已知的文件系统与部署都不会对 harness home 的祖先目录使用这种 mode。包测试固定了有界遍历顺序、不变的全量证明，以及非权限失败的大声传播。
